# Deployment

Two ways to run the same three images: **a VPS with Docker Compose** (one machine, you manage it) or **Render** (managed). Both use `infrastructure/docker/Dockerfile.api` (API and worker) and `Dockerfile.web`.

## What has and has not been tested

Tested, by replaying each image's commands in a clean copy of the repository: install from the lockfile, Prisma client generation, the production build, the API and worker entrypoints, the web server started with only a runtime `API_ORIGIN`, and the `/v1` proxy (auth header, cookies, a 12 MB body, streaming).

**Not tested:** the Docker builds themselves (no Docker was available), `docker-compose.prod.yml`, `render.yaml`, the Caddy setup, migrations against a real Postgres, and any run against a real LLM or bucket. Expect to fix small things on the first deploy. `render.yaml` is the least certain: render.com could not be reached when it was written, so plan names and a few field names come from memory. Render reports exactly what it rejects when you create the Blueprint.

## What every deployment needs

| Need | Detail |
|---|---|
| Domain | One hostname. The browser talks only to the web app; `/v1` is proxied to the API, so the refresh cookie is first party. |
| LLM | `LLM_API_KEY`, `LLM_MODEL_ANALYZE`, `LLM_MODEL_WRITE` (OpenAI is the only provider wired). |
| Object storage | An S3 or Cloudflare R2 bucket and an access key pair that can read and write it. No CORS setup is needed; downloads are signed URLs opened in a new tab. |
| Secrets | Generated by you, kept out of git: `JWT_SECRET`, `ADMIN_SEED_PASSWORD`, `ADMIN_BOOTSTRAP_TOKEN`, `TOTP_ENCRYPTION_KEY` (32 random bytes, base64), the database password. |

Environment variables are listed in `infrastructure/docker/.env.production.example`. The admin account is created from `ADMIN_EMAIL` and `ADMIN_SEED_PASSWORD` the first time the API starts. Use a long password (12 or more characters with upper, lower, digit and symbol); the seeding code does not check it.

## Option A: a VPS with Docker Compose

Caddy terminates HTTPS (certificates are issued and renewed automatically), then web, API, worker, Postgres and Redis run on a private Docker network. Only ports 80 and 443 are published. The worker runs LibreOffice, so give the machine at least 2 GB of RAM (a rough figure, not measured).

1. Point a DNS `A` record for your domain at the server's IP.

2. On the server, install Docker with the Compose plugin, allow only SSH, HTTP and HTTPS through the firewall, and clone the repository:
```bash
git clone https://github.com/whinkproducts-alt/resume-engine.git && cd resume-engine/infrastructure/docker
```

3. Create the env file and fill it in:
```bash
cp .env.production.example .env.production && chmod 600 .env.production
```
Generate the secrets with:
```bash
openssl rand -base64 32      # JWT_SECRET, ADMIN_BOOTSTRAP_TOKEN, TOTP_ENCRYPTION_KEY
```
```bash
openssl rand -hex 24         # POSTGRES_PASSWORD (hex, so it is safe inside a URL)
```

4. Build and start:
```bash
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build
```
The first build takes several minutes. The API applies the database migrations before it starts; the worker waits for the API to be healthy.

5. Watch it come up:
```bash
docker compose --env-file .env.production -f docker-compose.prod.yml ps
```
```bash
docker compose --env-file .env.production -f docker-compose.prod.yml logs -f api worker
```

6. Update later:
```bash
git pull && docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build
```

**Backups.** Everything stateful is in the `pgdata` volume (and `redisdata`, which only holds queued jobs). Résumés and exports are in your bucket. A database dump:
```bash
docker compose --env-file .env.production -f docker-compose.prod.yml exec -T postgres pg_dump -U resume resume_engine | gzip > backup-$(date +%F).sql.gz
```
Copy dumps off the machine, and test a restore once. No backup is scheduled for you.

## Option B: Render

`render.yaml` at the repository root defines the web service, the API, the worker (a background worker running the same image as the API), a Postgres database and a Key Value (Redis) instance with the `noeviction` policy BullMQ needs. The web service reaches the API over Render's private network.

1. Push this repository to GitHub (it is already there) and make sure the branch you want deployed contains `render.yaml`.
2. In Render: **New, Blueprint**, pick the repository and branch.
3. Render asks for every value marked `sync: false`: `ADMIN_EMAIL`, `ADMIN_SEED_PASSWORD`, the `LLM_*` model names, the `S3_*` values on the API and the worker, and `LLM_API_KEY` on the worker. Secrets are generated for `JWT_SECRET`, `ADMIN_BOOTSTRAP_TOKEN` and `TOTP_ENCRYPTION_KEY`.
4. Create it. If Render rejects a field or plan name, change it in `render.yaml` and re-sync.
5. After the first deploy, open the web service's URL. Add your domain under the web service's settings if you want one.

`TOTP_ENCRYPTION_KEY` is a Render generated value. It must decode to exactly 32 bytes; if admin 2FA enrollment answers `TOTP_NOT_CONFIGURED`, replace it with the output of `openssl rand -base64 32`.

Render's paid plans are used for the services and the database (free tiers sleep, and the free database expires). Check the current prices before creating anything.

## Smoke test (either option)

Replace `$HOST` with your domain (or the Render URL).

```bash
curl -s https://$HOST/v1/healthz        # {"ok":true}, through the web app's proxy to the API
```
```bash
curl -s https://$HOST/v1/readyz         # {"ok":true,"db":true}
```

Then in the browser:

1. Sign in with `ADMIN_EMAIL` and `ADMIN_SEED_PASSWORD`.
2. **Profiles**: create one, upload a base résumé named like `Jane Doe_Product_Acme.docx`, fill in the roster (roles, education), and add or import a few facts.
3. **New run**: paste a real job description (at least 200 characters). Watch the progress screen reach **Review**.
4. Download the DOCX and PDF and open them. This exercises the LLM, the worker, LibreOffice and the bucket together, so a failure here tells you which piece is misconfigured: the run's error code and the worker log name it.
5. **Admin, Users / Runs / Audit** load, and **Two factor** enrolls.

## Before you share the URL publicly

See the known gaps in [ARCHITECTURE.md](./ARCHITECTURE.md). The ones that matter for a public site:

- URL job descriptions are fetched from any address, which lets a user make the server request internal addresses.
- Admin 2FA can be enrolled but sign in does not ask for the code.
- There is no public signup, billing or password reset yet, so it is an invite-only deployment for now.
- There is no automatic backup, uptime monitoring or error tracking.
